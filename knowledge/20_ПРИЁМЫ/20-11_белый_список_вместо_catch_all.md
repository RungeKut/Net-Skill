# Сплит-туннель на белом списке

## Как устроено

Через туннель (VPS) идёт только трафик из белого списка `geosite`. Всё, что не попало в него, уходит в первый outbound (`direct`) — напрямую через провайдера. Явного catch-all-правила `direct` нет: непопавшее просто не встречает ни одного правила маршрутизации и отправляется в `direct` по умолчанию.

Порядок правил (Routing, `domainStrategy: AsIs`):

1. Inbound API панели → `api`
2. Локальная сеть и DNS-серверы → `direct`
3. Порт 53 → встроенный DNS Xray (`dns-out`)
4. BitTorrent → `blocked`
5. Приватные сети (`geoip:private`) → `direct`
6. **Белый список geosite** → `proxy` (VLESS+Reality на VPS):
   `geosite:youtube`, `google`, `google-gemini`, `telegram`, `instagram`,
   `facebook`, `whatsapp`, `discord`, `openai`, `twitter`, `netflix`,
   `tiktok`, `spotify`, `medium`, `bbc`, `linkedin`, `anthropic`,
   плюс отдельные домены сервисов, которых нет в готовых geosite
7. `geoip:telegram` / `twitter` / `facebook` → `proxy`
8. Всё, что не попало → `direct` (первый outbound, без явного правила).

## Почему это безопасность

Домен, не внесённый в белый список, вообще не виден на выходном узле. Даже если VPS скомпрометирован, логи утечки не покажут, какие RU-ресурсы посещались — они ушли напрямую.

## Страховка на выходном узле

На VPS добавлены правила:

- `geoip:ru` → `blocked`
- `geosite:category-ru` → `blocked`

Если что-то всё же дойдёт до VPS (ошибка маршрутизации, новый клиент с полным туннелем), RU-ресурсы будут заблокированы. Это страховка выходного IP, а не элемент сплит-туннеля.

## Риск

Новый нужный сервис молча пойдёт напрямую — не ломается, но не проксируется. Лечение: дополнить белый список, перезапустить Xray.

## Чем подтверждено

Схема в постоянной эксплуатации: основной inbound использует whitelist-маршрутизацию, второй inbound (полный туннель, другой UUID) имеет собственные правила с `category-ru → blocked` в начале. Белый список регулярно дополняется, ни одно изменение не ломало основной трафик.
